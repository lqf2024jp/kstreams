# 1. Processor API —— 自定义处理器

假设 Topic 中的数据：

```
order-topic

Key      Value

1001     apple
1002     banana
1003     orange
```

现在要求：

> 所有 Value 变成大写。

DSL 写法：

```java
builder.stream("order-topic")
       .mapValues(String::toUpperCase)
       .to("out-topic");
```

Processor API：

```java
public class UpperCaseProcessor
    extends ContextualProcessor<String,String,String,String>{

    @Override
    public void process(Record<String,String> record){

        String value = record.value().toUpperCase();

        context().forward(
            record.withValue(value)
        );
    }
}
```

Topology：

```
order-topic
      │
      ▼
UpperCaseProcessor
      │
      ▼
out-topic
```

为什么学这个？

因为以后你的：

```text
ProgressProcessor

MarkerProcessor

SnapshotCoordinator
```

全部都是：

Processor。

## 放到你的 CDC 项目中，它们分别负责什么？

| 技术              | 在你的项目中的作用               | 示例                                                         |
| ----------------- | -------------------------------- | ------------------------------------------------------------ |
| **Processor API** | 处理每一条 CDC 或 Marker 消息    | 收到 `ORDER_HEADER` 消息，更新 `TopicProgress`               |
| **StateStore**    | 保存运行状态                     | `ORDER_HEADER → lastJournalSequence=1004`，`checkpoint-001 → WAITING` |
| **Punctuator**    | 定时检查而不是只依赖新消息       | 每 30 秒扫描一次等待中的 Marker，检查是否超时或是否已满足 READY 条件 |
| **Exactly Once**  | 防止重复输出结果                 | `snapshot-audit-topic`、`snapshot-ready-topic` 不会因为重启重复发送 |
| **GlobalKTable**  | 动态维护 Job 与业务 Topic 的关系 | `JOB_ORDER → ORDER_HEADER、ORDER_DETAIL`，新增业务表时无需修改 YAML 或重启应用 |

你会发现，这五个知识点刚好对应一个完整的企业级 Kafka Streams 应用的五个核心能力：**处理事件、保存状态、定时调度、保证一致性、动态配置**。掌握了它们，你就能实现我们前面设计的 CDC Snapshot Coordinator。
